# TICC Architecture Documentation

**Date:** October 6, 2025  
**Version:** 20251006.1

## Overview

This document describes the architecture and implementation details of the TICC (Time Interval Counter) firmware. The TICC uses a TDC7200 chip to provide precise timestamp measurements with picosecond accuracy.

## Timestamp Generation

Timestamps are generated by combining a 100 µs coarse counter from a clock generated on the TICC board with the output from the TDC7200 chip, which provides the time-of-flight (TOF) from the event on the START to the count of the COARSE_CLOCK timer that is latched in the PICstop variable. TOF is *subtracted* from (PICstop × PICTICK_PS) to generate the timestamp.

### TOF Range Constraints

In theory, TOF could be up to 6 ms, which in picoseconds would require a 64-bit variable. However, the hardware design constrains the TOF range to between 300,000 ps (300 ns) and 100,300,000 ps (100.3 µs). This fits comfortably in a 32-bit variable, and we want to use 32-bit variables wherever possible because the Arduino is very slow at handling 64-bit variables.

## Main Loop Processing

The main loop iterates through the two channels looking for the INTB signal raised by the TDC7200 chip to indicate when a measurement is ready. The delay between PICstop being latched and INTB asserting is between 2330 ns and 2472 ns. Because of this variable delay and the fact that the two channels are checked for INTB sequentially, if both channels are active there is no guarantee which one will be processed first, and thus timestamps could be printed out of order or out of channel sequence. The pairing scheme mitigates this issue.

### Performance Characteristics

- **Idle loop iteration time:** ~2.5 to 3.0 µs (no INTB asserted)
- **Active loop iteration time:** ~1.7 to 1.9 ms (INTB asserted, including processing and printing at 115200 baud)
- **One-channel throughput:** ~540 measurements per second

## Timestamp Calculation

The timestamp calculation uses a mixed-radix accumulator approach:

- **Structure:** `Timestamp64 = {int32_t seconds, uint64_t picos}`
- **Algorithm:** `deltaT = dcount×PICTICK_PS - (tof_k - tof_{k-1})`
- **Accumulation:** `timestamp.picos += deltaT` with automatic carry/borrow to seconds
- **Precision:** Full picosecond precision (12 decimal places)
- **Performance:** 1250 measurements/second tested on one channel

This approach avoids 64-bit division/modulo operations, which are very expensive on 8-bit AVR microcontrollers.

## Data Types and Overflow Periods

| Variable | Type | Range/Overflow Period |
|----------|------|----------------------|
| **PICcount** | int64_t | Coarse counter, 100 µs per tick<br>Overflow: ~2.9×10¹¹ years (effectively never) |
| **PICstop** | int64_t | Captured PICcount value per event<br>Same range as PICcount |
| **tof** | int32_t | TDC7200 time-of-flight in picoseconds<br>Hardware range: ~300,000 to 100,300,000 ps<br>Can hold ~2.15 ms of picos |
| **timestamp.seconds** | int32_t | Accumulated integer seconds<br>Overflow: ±68 years from epoch |
| **timestamp.picos** | uint64_t | Fractional part, 0..(10¹²-1) picoseconds<br>Automatically normalized to stay within one second |

## Binary Mode (High-Throughput)

Binary mode provides maximum throughput for high-speed data collection:

- **Output format:** PICstop (lower 32 bits) + tof (32 bits) + channel + CRC
- **PICstop truncation:** ~4.97 days before overflow
- **User responsibility:** Must detect rollover externally for long-duration captures
- **Performance:** 1080 measurements/second @ 230400 baud

## Pairing Logic (Two-Channel Modes)

### Channel Synchronization

Each channel sets `new_ts_ready` when a fresh timestamp is computed.

### Mode-Specific Pairing

#### Interval and 3-Cornered Hat Modes
- Print once per pair when both channels are ready (A→B order)
- Clear both flags after printing
- Prevents mixing new and old samples, which can appear as ±1 s artifacts

#### Timestamp Mode
- Prints in ordered pairs with one-sample latency
- Two successive samples (across either channel) form a pair
- If both channels are present: chA then chB order
- If both from same channel: that channel is printed twice
- Handles single-channel and mismatched-rate cases without timeouts or configuration

## 3-Cornered Hat chC Synthesis

The 3-Cornered Hat mode synthesizes a third channel (chC) from the two physical channels:

- **chA and chB:** Printed as timestamps
- **chC:** Represents (B − A) but synthesized to look like a timestamp
- **Method:** Takes channel B's seconds and uses the signed delta fractional part
- **Benefit:** Avoids discontinuities at crossings and preserves three-corner-hat compatibility

## Printing Implementation (print.cpp)

The printing system is optimized for performance on 8-bit AVR:

- **Avoids Arduino printf:** Lacks 64-bit and floating point support
- **Uses optimized 32-bit division:** With reciprocal multiplication
- **Splits 12-digit picosecond fraction:** Into two 6-digit chunks
- **Single Serial.write() call per line:** For minimum overhead
- **Configurable options:** Decimal places (0-12) and wraparound digits
- **Performance:** ~560 timestamps/second

## Why Signed for Timestamp64.seconds

The seconds field uses signed integers for several important reasons:

- **Frequent subtraction operations:** `period = ts − last_ts; interval = B − A`
- **Negative results:** Can occur and signed integers avoid underflow
- **Special-case handling:** Eliminates need for complex underflow logic
- **Range adequacy:** int32_t range (±68 years) is sufficient for all measurement scenarios

## Hardware Timing Considerations

- **INTB assertion delay:** 2330 ns to 2472 ns after PICstop latching
- **Sequential channel checking:** Can cause ordering issues with dual-channel operation
- **Variable processing delays:** Require careful synchronization logic

## Performance Optimization

The firmware includes several optimization strategies:

1. **Early exit optimization:** Skips output processing when no new timestamps are ready
2. **Shared pairing framework:** Eliminates code duplication between pairing modes
3. **Global poll gating:** Consistent behavior across all output modes
4. **Function extraction:** Modular timestamp calculation and binary processing
5. **Critical section protection:** Proper interrupt handling for atomic operations
