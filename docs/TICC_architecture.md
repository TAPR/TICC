# TICC Architecture Documentation

**Date:** October 7, 2025  **Version:** 20251007.1

## Overview

This document describes the architecture and implementation details of the
TAPR TICC timestamping counter hardware and firmware. The TICC uses a TDC7200 chip to
provide precise timestamp measurements with picosecond accuracy.

## Hardware
There are two TDC7200 chips, one for each input channel.  We use only
a few of the TDC signal lines:
- START (event begins)
- STOP  (on 100 us boundary)
- INTB  (measurement complete)
- SPI 
- CLOCK

The TICC provides CLOCK from the external 10 MHz (100 ns) source and a 
COARSE_CLOCK running at 10 kHz (100 us).

The START signal is from the external device under test.  The STOP
signal is generated by the COARSE_CLOCK through a gating mechanism
described below.  COARSE_CLOCK provides timing in 100 us increments
and the TDC provides timing within those increments.

The TDC7200 has a minimum time interval constraint of 12 ns.  To ensure
that the STOP signal (derived from COARSE_CLOCK) meets this, a set of
logic gates ensure that the STOP signal comes from a COARSE_CLOCK tick
occurring at least 300 ns after the START signal.  That STOP signal is
fed to the TDC STOP pin to stop the measurement.  Its leading edge also
fires ISR on the Arduino that copies the value at that instant of the
100 us granularity timescale accumulator variable (PICcount) into the
channel's PICstop variable.  

### Notes: 
  - The STOP signal latches high until the TDC asserts INTB, so that STOP
    and the ISR never see more than one rising edge per measurement.
  - INTB assertion delay:** 2330 ns to 2472 ns after PICstop latching.

### TOF Range Constraints
The result of this is that the time interval (called time of flight, or
"tof") measured by the TDC chip is always within the range 300 ns to
100.3 us (300,000 to 100,300,000 picoseconds) and will fit within a 32
bit variable.
 
## Timestamp Generation
Timestamps are generated by combining the captured PICstop value with the
with the tof generated by the TDC chip.  To be precise, since PICstop represents 
the coarse tick *after* the START event, tof is *subtracted* from (PICstop * 100 us) 
to yield the timestamp.  The timestamp is stored in a struct consisting of a
32 bit int for the integer seconds and a 64 bit unsigned int for the fractional
part with 1 picosecond resolution (12 decimal places).

## Main Loop Processing
On each iteration, the main loop checks whether either or both TDC chips
have their INTB signals asserted to indicate they have completed a
measurement.  Because of the variable delay from the STOP signal until INTB 
assertion, there is no guarantee if both channels are active which one will 
be processed first, and thus timestamps could be printed out of order or out 
of channel sequence.

The processing loop is designed to correct this by checking INTB status
multiple times for both channels, and when both are present outputting the
earlier timestamp first.

### Performance Characteristics
- **Idle loop iteration time:** ~2.5 to 3.0 µs (no INTB asserted)
- **Active loop iteration time:** ~1.7 to 1.9 ms (INTB asserted, including
  processing and printing at 115200 baud)
- **One-channel throughput:** ~540 measurements per second

## Timestamp Calculation
The timestamp calculation uses a mixed-radix accumulator approach:

- **Structure:** `Timestamp64 = {int32_t seconds, uint64_t picos}`
- **Algorithm:** `deltaT = dcount×PICTICK_PS - (tof_k - tof_{k-1})`
- **Accumulation:** `timestamp.picos += deltaT` with automatic carry/borrow
  to seconds
- **Precision:** Full picosecond precision (12 decimal places)
- **Performance:** 1250 measurements/second tested on one channel

This approach avoids 64-bit division/modulo operations, which are very
expensive on 8-bit AVR microcontrollers.

## Binary Mode (High-Throughput)
Binary mode provides maximum throughput for high-speed data collection:

- **Output format:** PICstop (lower 32 bits) + tof (32 bits) + channel + CRC
- **PICstop truncation:** ~4.97 days before overflow
- **User responsibility:** Must detect rollover externally for long-duration
  captures
- **Performance:** 1080 measurements/second @ 230400 baud

## Pairing Logic (Two-Channel Modes)

### Channel Synchronization
Each channel sets `new_ts_ready` when a fresh timestamp is computed.

### Mode-Specific Pairing
#### Interval and 3-Cornered Hat Modes
- Print once per pair when both channels are ready (A→B order)
- Clear both flags after printing
- Prevents mixing new and old samples, which can appear as ±1 s artifacts

#### Timestamp Mode
- Prints in ordered pairs with one-sample latency
- Two successive samples (across either channel) form a pair
- If both channels are present: chA then chB order
- If both from same channel: that channel is printed twice
- Handles single-channel and mismatched-rate cases without timeouts or
  configuration

## 3-Cornered Hat chC Synthesis
The 3-Cornered Hat mode synthesizes a third channel (chC) from the two
physical channels:

- **chA and chB:** Printed as timestamps
- **chC:** Represents (B − A) but synthesized to look like a timestamp
- **Method:** Takes channel B's seconds and uses the signed delta fractional
  part
- **Benefit:** Avoids discontinuities at crossings and preserves
  three-corner-hat compatibility

## Printing Implementation (print.cpp)
The printing system is optimized for performance on 8-bit AVR:

- **Avoids Arduino printf:** Lacks 64-bit and floating point support
- **Uses optimized 32-bit division:** With reciprocal multiplication
- **Splits 12-digit picosecond fraction:** Into two 6-digit chunks
- **Single Serial.write() call per line:** For minimum overhead
- **Configurable options:** Decimal places (0-12) and wraparound digits
- **Performance:** ~560 timestamps/second

## Why Signed for Timestamp64.seconds
The seconds field uses signed integers for several important reasons:

- **Frequent subtraction operations:** `period = ts − last_ts; interval = B
  − A`
- **Negative results:** Can occur and signed integers avoid underflow
- **Special-case handling:** Eliminates need for complex underflow logic
- **Range adequacy:** int32_t range (±68 years) is sufficient for all
  measurement scenarios

## Hardware Timing Considerations
- **INTB assertion delay:** 2330 ns to 2472 ns after PICstop latching
- **Sequential channel checking:** Can cause ordering issues with
  dual-channel operation
- **Variable processing delays:** Require careful synchronization logic

## Performance Optimization

The firmware includes several optimization strategies:

1. **Early exit optimization:** Skips output processing when no new
timestamps are ready
2. **Shared pairing framework:** Eliminates code duplication between pairing
modes
3. **Global poll gating:** Consistent behavior across all output modes
4. **Function extraction:** Modular timestamp calculation and binary
processing
5. **Critical section protection:** Proper interrupt handling for atomic
operations
