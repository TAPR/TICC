## Detailed Breakdown

### Loop Detection Delay (~28 µs)

Time from INTB assertion until calculate_timestamp() is called. Includes:
- Serial.available() check
- check_reference_clock() call
- digitalRead() on both INTB pins
- Conditional logic to determine which channel(s) to process
- LED operations (SET_LED_0, SET_EXT_LED_0)

### Function Entry to ready_next() (~452 µs)

**Isolated component measurements:**
- channel->read() SPI: ~136 µs
- ready_next() SPI: ~30 µs
- **Expected total: ~166 µs**

**Actual measured: 452 µs**

**Additional time: ~286 µs**

However, `channel->read()` does much more than just SPI transactions. It includes 
the complete TOF (time-of-flight) calculation (lines 183-239 in tdc7200.cpp):
- Two 64-bit divisions (~1500-2500 cycles each = ~3000-5000 cycles total = ~190-310 µs)
- One 64-bit multiplication
- Multiple 32-bit calculations
- **Estimated TOF calculation time: ~100-150 µs**

**Revised breakdown:**
- SPI operations: ~166 µs
- TOF calculation in read(): ~100-150 µs  
- Integration overhead: ~136-186 µs
- **Total: ~402-502 µs** (matches measured 452 µs)

The integration overhead comes from:

1. **ISR Interruptions (largest contributor):**
   - PICcount ISR fires every 100 µs
   - During the 452 µs window, ISR fires 4-5 times
   - Each ISR interruption costs ~5-10 µs (context save/restore)
   - Total ISR overhead: ~20-50 µs

2. **Function Call Overhead:**
   - calculate_timestamp() call from main loop
   - channel->read() calls multiple internal SPI functions
   - Each function call: prologue/epilogue, stack operations
   - Nested call chains amplify overhead

3. **Memory Access Patterns:**
   - SPI operations require multiple memory reads/writes
   - Channel structure member access (not cache-friendly on AVR)
   - Global variable access (config, PICTICK_PS, etc.)

4. **Integration Effects:**
   - Code running in real system context vs. isolated tests
   - Compiler optimizations less effective with interrupts enabled
   - Memory contention between ISR and main code

### Post ready_next() Processing (~100 µs)

All code in calculate_timestamp() after ready_next() (lines 30-68 in timestamps.cpp):

**64-bit arithmetic operations:**
- dcount calculation (int64_t subtraction): ~8-16 cycles
- delta_ps = dcount × pictick_ps (int64_t multiplication): ~800-1200 cycles (~50-75 µs)
- delta_ps calculations (int64_t subtract/add): ~8-16 cycles each
- Accumulation with carry handling: varies based on path

**Other operations:**
- noInterrupts() / interrupts() calls
- PICstop reads from channel structure
- Conditional logic (if delta_ps >= 0)
- While loop for carry propagation (typically 0-1 iterations)
- Flag and counter updates

**Note:** The negative path (lines 53-64) with expensive 64-bit division/modulo 
is never executed because delta_ps is always positive in normal operation 
(see TICC_architecture.md for proof).

## Implications for Performance Optimization

### Current Bottleneck Priority

1. **64-bit math operations (200-250 µs, 35-43%)** ← Largest, potential optimization target
   - TOF calculation: ~100-150 µs (two divisions, one multiplication)
   - Timestamp accumulation: ~100 µs (one multiplication, add/subtract)
2. **SPI operations (166 µs, 29%)** ← Already optimized
3. **Integration overhead (136-186 µs, 23-32%)** ← Difficult to optimize
4. **Loop detection (28 µs, 5%)** ← Already efficient

### Optimization Possibilities

**Limited options remaining:**

1. **Reduce ISR frequency** - Not feasible (100 µs coarse timing is required)
2. **Optimize 64-bit math** - Possible but complex:
   - Use fixed-point arithmetic
   - Split calculations differently
   - Use lookup tables for common values
3. **Inline critical functions** - Marginal gains (function call overhead is small)
4. **Assembly optimization** - High effort, modest gains

**Reality:** The system is approaching fundamental AVR performance limits. Further 
significant improvements would require architectural changes (faster MCU, hardware 
acceleration, etc.).

### Rate-Dependent Blocking Behavior

**Experimental validation at varying measurement rates:**

| Rate (Hz) | Period (µs) | Behavior |
|-----------|-------------|----------|
| <480 | >2083 | Stable, minimal blocking |
| 480 | 2083 | Processing time starts increasing slightly |
| 590 | 1695 | At system limit, occasional instability |
| 600 | 1667 | Increased instability, overlapping events |
| 610 | 1639 | More pronounced instability |
| 620+ | <1613 | Complete pattern breakdown |

### Interpretation

The measured "print time" of ~800-1200 µs represents:
1. **Formatting time:** ~125-200 µs (varies with digit count/wrap)
2. **Serial.write() blocking:** ~600-1000 µs waiting for UART TX buffer space

At high measurement rates (>480 Hz), the 64-byte UART TX buffer stays fuller because 
the hardware is continuously transmitting previous timestamps. Serial.write() blocks 
until sufficient buffer space is available.

**Why 230400 baud helps so little:**
- Formatting time (~200 µs) unchanged
- Processing time (580 µs) unchanged
- Serial.write() blocking reduces from ~1000 µs to ~500 µs
- But system is still limited by buffer drain rate
- Net improvement: only ~6% throughput gain

**Maximum sustainable rate @ 115200:** ~580-590 measurements/second  
**Maximum sustainable rate @ 230400:** ~620 measurements/second

## Conclusion

The GPIO timing instrumentation provides definitive, ground-truth measurements of 
TICC processing performance:

- **Total processing: 580 µs** (calculation only, measured end-to-end)
- **64-bit math operations: 200-250 µs (35-43% of processing)** - largest computation bottleneck:
  * TOF calculation with two 64-bit divisions: ~100-150 µs
  * Timestamp accumulation with one 64-bit multiplication: ~100 µs
- **SPI operations: 166 µs (29% of processing)** - already optimized
- **Integration overhead: 136-186 µs (23-32% of processing)** - ISR interruptions + function calls
- **Loop detection: 28 µs (5% of processing)** - efficient

**Print phase measurements:**
- **Total print time: 800-1200 µs** (varies with output length)
  * Formatting: ~125-200 µs
  * Serial.write() blocking: ~600-1000 µs (waiting for UART buffer space)
- **Rate-dependent behavior:** At high rates (>480 Hz), Serial.write() blocking 
  increases as buffer stays fuller
- **Maximum sustainable rate:** ~580-590 measurements/second @ 115200 baud

These measurements reveal that:
1. **During calculation:** 64-bit arithmetic (particularly TOF divisions) is the 
   dominant computational bottleneck
2. **During output:** Serial.write() blocking waiting for UART buffer space is the 
   dominant system bottleneck
3. The system is approaching fundamental AVR performance limits for 64-bit math on 
   an 8-bit architecture, AND serial I/O throughput limits
