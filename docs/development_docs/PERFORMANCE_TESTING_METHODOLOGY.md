## Overview

This document describes the methodology used for accurate performance measurement of Arduino-based firmware, specifically developed for characterizing TDC7200 SPI read optimizations.

## Two-TICC Timing Method

### Concept

Use one TICC to measure timing pulses generated by another TICC under test.

### Hardware Setup

```
Test TICC (instrumented firmware)
  Pin A0 → Measurement TICC Channel A Input
  
Measurement TICC (normal firmware)
  - Configure for Timestamp mode
  - Captures picosecond-accurate timestamps
```

### Timing Pulse Generation

**For synthetic tests (no input signal):**
- Generate brief pulse (~2 µs) every N iterations
- Time between timestamps = time for N iterations
- Divide by N for average time per iteration

**For real signal tests:**
- Generate pulse at specific point in processing
- Measure intervals between pulses
- Accounts for input signal rate

### Advantages

✅ Picosecond timing accuracy  
✅ Statistical analysis from many samples  
✅ No oscilloscope required  
✅ Perfect for measuring fast code sections (~100 µs)  

### Limitations

❌ Can only measure rising edges (not pulse widths)  
❌ Requires two TICCs  
❌ Analysis requires post-processing  
❌ Challenging to measure live processing (includes wait time)  

### Best For

- Isolated code section timing (synthetic tests)
- Comparing relative performance
- Long-term statistical analysis
- Sub-microsecond precision needed

## Oscilloscope Method

### Concept

Generate pulses HIGH during code execution, measure pulse width on oscilloscope.

### Hardware Setup

```
Test TICC (instrumented firmware)
  Pin A0 → Scope CH1 (primary measurements)
  Pin A7 → Scope CH2 (secondary/comparison measurements)
  
Oscilloscope
  - 2-channel recommended
  - Trigger on CH1 rising edge
  - Measure pulse widths or time deltas
```

### Pulse Generation Methods

**Method A: Pulse Width**
```cpp
TIMING_PIN_HIGH;    // Start of code section
// ... code to measure ...
TIMING_PIN_LOW;     // End of code section
```
Scope measures pulse width = execution time

**Method B: Two-Pulse Delta (for complex measurements)**
```cpp
TIMING_PULSE();     // CH1: Brief pulse at start
// ... code to measure ...
TIMING_PULSE2();    // CH2: Brief pulse at end
```
Scope measures time delta from CH1 to CH2 = execution time

### Advantages

✅ Direct visual confirmation  
✅ Pulse width = execution time (no calculation)  
✅ Easy to interpret  
✅ Works well with real input signals  
✅ Simultaneous dual measurements (2-channel scope)  
✅ Scope statistics provide min/max/mean  

### Limitations

❌ Requires oscilloscope  
❌ Lower precision than TICC (~1-10 ns vs picoseconds)  
❌ Manual measurement/recording  

### Best For

- Verification of other measurement methods
- Real-world processing time with live signals
- Visual confirmation of optimizations
- Component timing breakdown (dual channel)

## Synthetic vs Live Signal Testing

### Synthetic Testing

**Concept:** Run code in tight loop independent of input signals

**Advantages:**
- Isolates specific code sections
- Maximum throughput testing
- No wait time for inputs
- Repeatable conditions

**Implementation:**
```cpp
while(1) {
  if (counter % N == 0) generate_timing_pulse();
  run_test_function();
  counter++;
}
```

**Best for:** Measuring isolated code performance (SPI reads, calculations, etc.)

### Live Signal Testing

**Concept:** Measure during normal operation with real input signals

**Advantages:**
- Real-world conditions
- Includes all overhead
- Tests actual use case
- Reveals rate-limiting factors

**Implementation:**
```cpp
if (measurement_ready) {
  generate_timing_pulse_start();
  process_measurement();
  generate_timing_pulse_end();
}
```

**Best for:** End-to-end performance, maximum throughput limits, real bottlenecks

## Statistical Analysis

### From TICC Method

Collect 30+ timestamp samples, calculate intervals:

```python
intervals = np.diff(timestamps)
execution_times = intervals / TIMING_SAMPLE_INTERVAL
print(f"Mean: {np.mean(execution_times)*1e6:.2f} µs")
print(f"Std Dev: {np.std(execution_times)*1e6:.2f} µs")
```

### From Oscilloscope

Use scope's built-in statistics:
- Mean: Average execution time
- Min/Max: Best/worst case timing
- Range: Timing variation (jitter)

## Dealing with Timing Jitter

### Sources of Variation

1. **Interrupt Service Routines**
   - PICcount ISR every 100 µs: adds 5-20 µs
   - Other interrupts: variable overhead

2. **AVR Pipeline Effects**
   - Branch prediction
   - Instruction timing variations
   - Memory access patterns

3. **External Factors**
   - SPI clock stability
   - Power supply variations
   - Temperature effects

### Minimizing Jitter

For most accurate measurements:
- Collect large sample sizes (100+)
- Report min/mean/max
- Use statistical outlier detection
- Test under controlled conditions

## Best Practices

### Test Design

1. **Start with synthetic tests** - Isolate the code section of interest
2. **Verify with scope** - Visual confirmation of results
3. **Test live conditions** - Measure real-world performance
4. **Collect statistics** - Multiple samples for confidence
5. **Document everything** - Methodology, configuration, results

### Avoiding Common Pitfalls

❌ Don't measure full loop when testing specific functions  
❌ Don't forget to account for wait time in live tests  
❌ Don't trust single measurements - get statistics  
❌ Don't assume Arduino IDE recompiled - verify or clean build  
❌ Don't ignore timing jitter - it reveals system behavior  

### Configuration Management

Use header files with conditional compilation:
```cpp
// timing_test.h
#define TIMING_TEST_MODE_X
//#define TIMING_TEST_MODE_Y

// In code:
#ifdef TIMING_TEST_MODE_X
  // Instrumentation
#endif
```

Advantages:
- Single source tree
- Easy A/B comparison
- Document configuration in header
- Zero overhead when disabled
