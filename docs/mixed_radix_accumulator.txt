Great question. You’re right that the absolute timestamp for each event is:

T_abs(ps) = PICstop * PICTICK_PS − tof − fudge

So why did I propose using delta_ps and accumulating?

Short answer:


- Computing absolute T_abs each time is fine functionally, but turning that into printable seconds with 12 decimal places typically requires a 64-bit divide/mod by 1e12 per event (to split into seconds and subsecond ps). On an 8-bit AVR, those divisions/mods are very slow and were the key reason your “simpler” int64 approach ran much slower.

- By accumulating deltas, we maintain a mixed-radix timestamp (seconds + sub_ps) without doing any 64-bit division or modulo, just adds/subtracts and an occasional compare/subtract by 1e12. That’s much faster on the Mega 2560.

- The accumulated timestamp still equals the absolute formula; we’re just computing it incrementally in a CPU-friendly way.

How it works, step by step:


1. 
Absolute timestamp model

For event i:

T_i_abs = PICstop_i * 10,000,000 − tof_i − fudge


If you compute this absolute value per event, to print you usually do:


	- seconds = T_i_abs / 1e12

	- sub_ps = T_i_abs % 1e12

Those two operations (64-bit divide and modulo by 1e12) are expensive.


2. 
Incremental (delta) model

Consider the difference between consecutive absolute timestamps:

T_i_abs − T_{i−1}abs

= (PICstop_i − PICstop{i−1}) * 10,000,000 − (tof_i − tof_{i−1}) − (fudge_i − fudge_{i−1})


Since your fudge is static, that term is zero. Also, you clarified tof is an absolute per-event measurement (not cumulative). That means we should NOT difference tof. Instead, we use:


delta_ps = (PICstop_i − PICstop_{i−1}) * 10,000,000 − tof_i


Why? Because the absolute formula for the accumulated timeline from one event to the next increases exactly by that amount:


	- PICcount advances by dcount ticks, contributing dcount * 10,000,000 ps forward.

	- The measured event occurred tof_i ps before the next tick, so the final event time is that much earlier than the tick boundary we’re referencing, hence subtract tof_i.

Then we add delta_ps to our accumulator:


	- sub_ps += delta_ps

	- while sub_ps >= 1e12: sub_ps -= 1e12; seconds++

	- if sub_ps goes negative (rare edge), borrow from seconds

This yields the same total timestamp as computing T_abs each time, but we never do a divide/mod by 1e12.



3. 
Why this is faster on AVR




- 64-bit division/modulo by 1e12 each event is very slow in software on an 8-bit CPU.

- The delta path uses:
	- one 32x32→64 multiply (dcount * 10,000,000)

	- a few 64-bit adds/subs

	- a compare and at most one subtract of 1e12 per event for carry

These operations are much cheaper, which is why your older seconds+fractional struct (that implicitly avoids big divides) ran faster.



1. Correctness and monotonicity


- The delta accumulation produces the same monotonic timeline as the absolute expression. You can verify by starting from zero and summing all delta_ps; you’ll land at the same T_abs you’d get from the formula at that event.

- Because tof can be slightly more than one 100 µs tick, delta_ps could be negative in rare edge cases (e.g., two events very close together in ticks). The code handles that by borrowing from seconds to keep the total monotonic.


1. Printing advantage


- With the mixed-radix accumulator, the timestamp is already in seconds + sub_ps (0..1e12−1), which prints directly:
	- print seconds (with optional wrap via conditional subtract)

	- print sub_ps as a zero-padded 12-digit integer


- No need to split an absolute 64-bit picosecond counter into seconds and remainder via division/modulo.

Bottom line:


- You’re not “losing” the absolute formula; you’re computing the same result through an incremental path that’s much cheaper on an 8-bit CPU.

- This is why the delta-based mixed-radix approach should let you meet or beat 500 measurements/sec while still supporting full picosecond precision and long monotonic runs.
